# 原版客户端登录接口完整说明

## 1. 总览

原版客户端登录不是“只调一个登录接口”。

完整链路通常是：

1. 建立连接
2. 先尝试本地 `authinfo + heartbeat`
3. 失败后再尝试账号密码 `login.auth`
4. 没账号或 `Uin<=1` 时走 `login.reg`
5. 登录成功后必须再跑 `baseinfo.update`
6. 如果开启了安全登录验证，还会追加 `baseinfo.set_DeviceID` 等流程

所以从客户端视角看：

- `login.reg` / `login.auth` 负责拿 `authinfo`
- `heartbeat` 负责用 `token` 恢复会话
- `baseinfo.update` 才负责把账号完整数据同步进来

## 2. 传输方式

客户端登录链混用了两种通道：

1. WebSocket RPC
2. HTTP RPC

其中：

- 主登录链核心是 WebSocket RPC
- 找回密码、密保验证这类流程大量走 HTTP RPC

## 3. WebSocket RPC 报文格式

客户端通过 `self:remote_call(...)`、`self.cluster.xxx.xxx(...)` 发 RPC。

从客户端侧可归纳为：

请求：

```lua
[0, service, method, seq, ts, args]
```

返回：

```lua
[1, service, method, seq, ts, payload]
```

常见字段含义：

- `service`：如 `login`、`baseinfo`
- `method`：如 `auth`、`reg`、`update`
- `args`：参数列表
- `payload[1]`：错误码
- `payload[2...]`：业务返回值

## 4. 登录主流程

## 4.1 入口函数

主入口在：

- [`client.lua`](/sdcard/-z/minisj/assets/luascript/client.lua) `login(self, Uin, Passwd)`

它会按下面顺序尝试登录。

## 4.2 分支顺序

### 4.2.1 单机模式

如果：

```lua
gIsSingleGame == true
```

则直接走：

```lua
self:reg(Passwd)
```

也就是单机模式沿用“注册”入口去初始化本地账号。

### 4.2.2 本地没有有效迷你号

如果当前 `Uin <= 1`，客户端认为本地没有有效账号，直接走：

```lua
self:reg(Passwd)
```

### 4.2.3 先尝试密保问题自动登录

如果本地 `current.question` 存在，则先调用 HTTP：

```lua
self:http_rpc('passwd', 'question_verify', {...})
```

如果返回 `authinfo`，客户端不会立刻认为登录完成，而是：

1. 把 `conn.token = authinfo.token`
2. 立即调用 `conn:heartbeat()`
3. 心跳成功才把自己标记为 `authed`

### 4.2.4 再尝试本地缓存 authinfo 自动登录

如果本地 `current.authinfo` 存在，并且至少有：

- `Uin`
- `token`
- `sign`

客户端会：

1. 把 `conn.token = authinfo.token`
2. 直接调用 `conn:heartbeat()`
3. 心跳成功后恢复会话

### 4.2.5 最后才走账号密码登录

如果前两步都没成功，才调用：

```lua
self.cluster.login.auth({...})
```

成功后写入：

- `conn.token`
- `conn.sign`
- `conn.other`
- 本地 `current.Passwd`

### 4.2.6 登录后统一做数据同步

无论前面是：

- `question_verify`
- 本地 `authinfo`
- `login.auth`
- `login.reg`

最后都会继续执行：

```lua
self:get_account_info(Uin)
self:data_update(true)
```

这一步才是真正把账号资料、货币、角色、家园树、额外状态同步进来。

## 5. 注册接口

## 5.1 `login.reg`

客户端调用位置：

- [`client.lua` `reg()`](/sdcard/-z/minisj/assets/luascript/client.lua)

调用形式：

```lua
self.cluster.login.reg(info, account.Account.RoleInfo)
```

服务：

```text
service = login
method  = reg
```

## 5.2 客户端构造的参数

第 1 个参数 `info`：

- `DeviceID`
- `ApiId`
- `AccountName`
- `Longitude`
- `Latitude`
- `CltVersion`
- `CltType`
- `OpenString`
- `Passwd`
- `Country`

第 2 个参数：

- `account.Account.RoleInfo`

也就是角色信息对象，至少会带：

- `NickName`
- `Model`
- `SkinID`

## 5.3 特殊逻辑

如果：

```lua
info.Passwd == '0'
```

客户端会自己生成一个临时密码：

```lua
local now_  = getServerNow()
local auth_ = gFunc_getmd5(now_)
info.Passwd = string.sub(auth_, 2, 9)
```

说明：

原版客户端不允许把字符串 `"0"` 当成最终注册密码直接发出去。

## 5.4 成功后客户端怎么处理

如果 `login.reg` 返回 `code == ErrorCode.OK`，客户端会：

1. `conn.authed = true`
2. 保存 `authinfo.token`
3. 保存 `authinfo.sign`
4. 保存 `authinfo.other`
5. `account:setuin(authinfo.Uin)`
6. 本地保存 `current = {Uin, Passwd}`
7. 继续执行 `data_update(true)`

## 6. 账号密码登录接口

## 6.1 `login.auth`

客户端调用位置很多，主要有：

- 普通登录
- 切换账号
- openid/openstring 登录
- 重设密码后重新登录

最常见调用在：

- [`client.lua` `login()`](/sdcard/-z/minisj/assets/luascript/client.lua)

调用形式：

```lua
self.cluster.login.auth({...})
```

服务：

```text
service = login
method  = auth
```

## 6.2 常见参数集合一：按 Uin + Passwd 登录

客户端最常发的一组字段：

- `Uin`
- `Passwd`
- `ApiId`
- `CltVersion`
- `DeviceID`
- `Country`

## 6.3 常见参数集合二：按 AccountName + OpenString 登录

在切换账号 / openid 风格登录时，客户端会发：

- `AccountName`
- `OpenString`
- `ApiId`
- `CltVersion`
- `RoleInfo`
- `DeviceID`
- `Longitude`
- `Latitude`
- `CltType`
- `Country`
- `extra`

其中 `extra` 可能带第三方平台信息，例如 facebook：

- `platform`
- `id`
- `nickname`

## 6.4 常见参数集合三：切换账号时带 `isswitch`

在 `setAccountPasswd()` 之后重新登录时，还会额外带：

- `isswitch = true`

## 6.5 登录成功后客户端怎么处理

成功后客户端统一依赖返回的 `authinfo` 字段：

- `Uin`
- `token`
- `sign`
- `other`
- `isnewuser`

并执行：

1. `conn.authed = true`
2. `conn.token = authinfo.token`
3. `conn.sign = authinfo.sign`
4. `conn.other = authinfo.other`
5. `self.account.islogin = true`
6. 必要时 `account:setuin(authinfo.Uin)`
7. 继续 `data_update(true)`

## 7. 心跳接口

客户端调用：

```lua
conn:heartbeat()
```

用途：

- 用已有 `token` 恢复会话
- 校验当前 `token` 是否还有效
- 自动登录时比 `login.auth` 更优先

客户端使用场景：

1. 本地缓存了 `authinfo`
2. `question_verify` 返回了 `authinfo`
3. `requestEnterGameWithAuthInfo(authinfo)`
4. `switchAccountByAuthInfo(authinfo)`

换句话说：

只要客户端手上已经有 `authinfo.token`，它优先尝试 heartbeat，而不是重新发账号密码。

## 8. 登录后强制同步接口

## 8.1 `baseinfo.update`

客户端调用位置：

- [`client.lua` `do_data_update()`](/sdcard/-z/minisj/assets/luascript/client.lua)

调用形式：

```lua
self:remote_call('baseinfo', 'update', {
    ApiID = ...,
    Longitude = ...,
    Latitude = ...,
    CltVersion = ...,
    CltType = ...,
    RoleInfo = ...,
    extra = {...},
    birthday = ...,
})
```

服务：

```text
service = baseinfo
method  = update
```

## 8.2 参数内容

固定字段：

- `ApiID`
- `Longitude`
- `Latitude`
- `CltVersion`
- `CltType`

可选字段：

- `RoleInfo`
- `birthday`

`extra` 子表通常带：

- `Country`
- `DeviceToken`
- `DeviceVender`
- `DeviceModel`
- `DeviceID`
- `CltApiID`
- `CltLang`
- `DeviceSystem`

## 8.3 客户端对返回值的依赖

只要 `baseinfo.update` 返回成功，客户端会：

1. `obj.svrinfo = svrinfo`
2. `obj:OnAccountDirty()`
3. `obj:makeBuddyDetail()`
4. 更新
   - `self.isnewDeviceID`
   - `self.versionlow`
5. 继续执行 `safeverify()`

也就是说客户端把 `baseinfo.update` 返回的 `svrinfo` 视为登录完成后的关键状态。

## 9. 安全登录相关接口

这些接口都属于“登录链延伸部分”，不是每次登录都调，但都属于原版客户端登录体系的一部分。

## 9.1 `baseinfo.set_loginsafeverify`

客户端调用：

```lua
self:remote_call('baseinfo', 'set_loginsafeverify', state)
```

用途：

- 开关安全登录验证

## 9.2 `baseinfo.set_DeviceID`

客户端调用：

```lua
self:remote_call('baseinfo', 'set_DeviceID', DeviceID)
```

用途：

- 安全验证成功后，把当前设备号写回服务端

客户端在 `safeverify()` 成功后会调用它。

## 9.3 `baseinfo.set_guest`

客户端调用：

```lua
self:remote_call('baseinfo', 'set_guest', flag)
```

用途：

- 设置游客标记

## 10. 文字密保 / 安全问题接口

## 10.1 `passwd.question_verify`

客户端调用形式：

```lua
self:http_rpc('passwd', 'question_verify', {
    Uin = Uin,
    key = question_key,
    value = question_value,
    apiid = LuaInterface:getApiId(),
    DeviceID = ClientMgr:getDeviceID(),
})
```

特点：

- 这是 HTTP，不是 `remote_call('baseinfo', ...)`
- 返回成功后客户端期望得到 `info.authinfo`

成功后后续流程不是直接进游戏，而是：

1. 取出 `info.authinfo`
2. 用 `authinfo.token` 去 heartbeat
3. heartbeat 成功后再 `data_update(true)`

## 10.2 `baseinfo.question_set`

客户端调用：

```lua
self:remote_call('baseinfo', 'question_set', idx, key, value)
```

说明：

- `idx` 只能是 `1` 或 `2`
- `value` 在客户端先做 md5

## 10.3 `baseinfo.auth_set`

客户端调用：

```lua
self:remote_call('baseinfo', 'auth_set', list)
```

客户端约定格式：

- `{0, passwd}`：设置密码
- `{1, key, value}`：问题 1
- `{2, key, value}`：问题 2

客户端会先把问题答案 md5 后再发。

成功后如果本次 `auth_set` 里带了密码，客户端会立即重新登录。

## 11. 改密 / 找回密码接口

这部分原版客户端明显混用了 HTTP 与 WebSocket。

## 11.1 在线改密码

客户端调用：

```lua
self:remote_call('baseinfo', 'passwd', passwd)
```

用于当前已登录账号直接改密码。

成功后客户端会：

1. 保存本地新密码
2. 断线重连
3. 再走一次 `login(Uin, passwd)`

## 11.2 手机验证码找回

客户端调用 HTTP：

- `passwd.smsreset`
- `passwd.smsverify`
- `passwd.passwd_by_sms`

典型调用：

```lua
self:http_rpc('passwd', 'smsreset', {phonenum = phonenum, lang = ...})
self:http_rpc('passwd', 'smsverify', {phonenum = phonenum, code = verify_code, lang = ...})
self:http_rpc('passwd', 'passwd_by_sms', {
    Uin = Uin,
    passwd = passwd,
    code = code,
    CltVersion = LuaInterface:getCltVersion(),
    lang = ...,
    question = question,
})
```

## 11.3 邮箱验证码找回

客户端调用 HTTP：

- `passwd.emailreset`
- `passwd.emailverify`
- `passwd.passwd_by_email`

典型调用：

```lua
self:http_rpc('passwd', 'emailreset', {email = email, lang = ...})
self:http_rpc('passwd', 'emailverify', {email = email, code = verify_code, lang = ...})
self:http_rpc('passwd', 'passwd_by_email', {
    Uin = Uin,
    passwd = passwd,
    code = code,
    CltVersion = LuaInterface:getCltVersion(),
    lang = ...,
    question = question,
})
```

## 11.4 密码错误上报接口

客户端代码里还出现过：

```lua
self:http_rpc('passwd', 'not_ok', {...})
```

但当前 Lua 里这段被注释掉了，不一定总会真正发出。

它本质是登录失败时的辅助上报，不是主登录流程必需接口。

## 14. 切换账号相关登录接口

## 14.1 `switchAccountByOpenString`

客户端调用的核心接口还是：

```lua
self.cluster.login.auth({
    AccountName = accountname,
    OpenString = openstring,
    ApiId = ...,
    CltVersion = ...,
    RoleInfo = ...,
    DeviceID = ...,
    Longitude = ...,
    Latitude = ...,
    CltType = ...,
```

成功后继续：

```lua

```

## 14.2 `switchAccountByAuthInfo`

如果客户端手头已经有老账号留下的 `authinfo`，它会直接：

1. `conn.token = authinfo.token`
2. `conn:heartbeat()`
3. `self:data_update()`

也就是说切换账号不一定重新走密码登录。

## 17. 原版客户端真实依赖的登录返回字段

从客户端代码看，`login.reg` / `login.auth` / `question_verify` 最核心的返回对象是 `authinfo`。

客户端明确依赖这些字段：

- `Uin`
- `token`
- `sign`
- `other`
- `isnewuser`

其中：

- `token`：后续 heartbeat 直接用
- `sign`：客户端会保存，但登录完成的关键还是 `token + heartbeat`
- `other`：客户端保存到 `conn.other`
- `isnewuser`：用于决定是否提示 `first_login`

## 18. 原版客户端真实依赖的 `baseinfo.update` 返回内容

客户端在 `data_update()` 中直接把返回值命名成 `svrinfo`，并依赖它至少包含：

- `needauthcity`
- `isnewDeviceID`
- `versionlow`

此外还会整体写入：

```lua
obj.svrinfo = svrinfo
```

所以从客户端视角看，`baseinfo.update` 返回的不只是“个人资料”，而是登录完成后的核心服务端状态对象。

## 19. 最小可用登录链

如果只从原版客户端角度抽“最小闭环”，最少要覆盖：

1. `login.reg`
2. `login.auth`
3. `heartbeat`
4. `baseinfo.update`

如果要覆盖“完整登录生态”，还要补：

5. `passwd.question_verify`
6. `baseinfo.question_set`
7. `baseinfo.auth_set`
8. `baseinfo.passwd`
9. `passwd.passwd_by_sms`
10. `passwd.passwd_by_email`
11. `baseinfo.set_loginsafeverify`
12. `baseinfo.set_DeviceID`
13. `baseinfo.bind`
14. `baseinfo.bindopenid`
15. `baseinfo.unbindopenid`
16. `baseinfo.bindphone / bindemail`
17. `baseinfo.verify_phone_code / verify_email_code`
18. `baseinfo.idcard_auth`

## 20. 结论

原版客户端登录体系的核心不是“一个登录接口”，而是下面这套组合：

- `login.reg`
- `login.auth`
- `heartbeat`
- `baseinfo.update`
- `passwd.*`
- `baseinfo.*` 中与账号安全、绑定、实名、设备验证相关的一串接口
